# Full-repo audit — October 2026

Fourth review. Unlike the first three it **ran the system**: a clean install, the full
suite, a headless-browser pass over every page, and — for the first time — the Postgres
path against a real Postgres 16. Four area reviews (money, API security, outreach,
discovery) ran in parallel; every finding below was reproduced by a probe or read end to
end before being listed.

The headline: the 456-test suite and the earlier "remediated" claims hold **only on the
in-memory store and against mocks**. The in-memory store never yields to the event loop,
so requests are serialized and concurrency bugs are invisible to the tests. Several
defects are logic, not missing live validation.

The tables describe each finding as it was found. What was done about each one is in the
fix log at the bottom of this file.
Evidence: **run** = reproduced by executing code here, **read** = traced in the source.

## Contracts shared between fix streams

These are fixed points so parallel work lines up. Do not change them without updating
this section.

1. **Manual payouts (no custody).** Money never passes through the platform.
   - A payout is disbursed through `resolveRail(merchant, method)`. An automated rail is
     used only when the **merchant** has connected their own credentials for it. No
     platform-wide rail credentials exist. The `mock` rail resolves only when
     `NODE_ENV !== "production"`.
   - Otherwise the payout is **manual**: on batch approval it moves to status
     `awaiting_payment` (entries stay reserved). The merchant pays from their own account.
   - `GET /payouts/batches/:id/export?format=paypal|wise|csv` returns `text/csv`
     (role: approve). `paypal` = PayPal mass-pay layout, `wise` = Wise batch layout,
     `csv` = generic (affiliate, email, method, account reference, amount, currency, payout id).
   - `POST /payouts/:payoutId/mark-paid` body `{ reference?: string }` settles the
     reservation and sets `paid`. `POST /payouts/:payoutId/mark-failed` body
     `{ reason: string }` releases the reservation and sets `failed`. Both role: approve,
     both valid only from `awaiting_payment`.
   - `Payout.status` gains `"awaiting_payment"`.
2. **Database primitives.** `db.transaction(fn)` gives `fn` a handle bound to ONE
   connection and rolls back on throw in both adapters. `db.withLock(key, fn)` serializes
   callers on `key` across processes (Postgres advisory lock; in-memory async mutex).
   Uniqueness is declared once and enforced by both adapters.
3. **Per-merchant send lock.** `packages/recruitment` exposes one seam,
   `withMerchantLock(deps, merchantId, fn)`, wrapping every path that queues or sends
   (cycle, launch, send-reply). It delegates to `deps.db.withLock`.
4. **Affiliate magic link.** Emailed links stay `{app}/#/portal/verify?token=…`. The web
   app handles that route by posting the token to `POST /auth/affiliate/verify` and
   storing the session. Tokens are single-use; a used or expired link shows a
   "send me a new link" form.
5. **Outbound fetch safety.** One helper in `packages/integrations/src/net-guard.ts`
   (public-address check after DNS resolution, manual redirect following with re-check,
   timeout, body cap) is used by every fetch of a URL that came from a page, an import
   or a tenant — including outbound webhooks.
6. **Ownership.** `package.json`, `package-lock.json`, `.env.example`, and every `*.md`
   are owned by the coordinator. Streams report needed dependencies and new env vars.
